## 2. 데이터가 어디 사는가

저장소 = Cloudflare R2. 바인딩 이름 **`R2`**(정확히 이 이름이라야 한다). 키는 전부 `booking/` 밑에만 쓴다.

```
booking/roster.json          명단   { "1234": {g:"a", n:"홍길동"}, ... }
booking/stock.json           공연·날짜·수량
                             { labels:{a:"9/12",…},
                               shows:{ a:{title,date,time,hall}, … },
                               cap:{ a:{double:5,twin:5}, … } }
booking/bk/<뒷4자리>.json     선택 1건 = 파일 1개
```

`bk/*.json`에는 본문 말고 **메타(customMetadata)** 도 같이 붙는다: `{ g:구분, t:종류, at:시각 }`.
집계는 목록 조회(`list`) **1회**로 끝난다 — 파일을 하나씩 열지 않는다. 이게 §4-a 성능의 전제다.

**`g`(구분) = 공연 1종 = 숙박일 1일.** 「예매일 당일 숙박」이 상품 조건이라 공연 날짜가 곧 체크인 날짜다.
체크아웃은 저장하지 않는다 — `stayOf()`가 `date + 1`로 매번 계산한다(월·해 넘김은 `test.mjs` [8]이 잡는다).

기본값(홍보물 실제 값 · 총 40세트) — a 조재혁 9/12 더블5·트윈5 / b 트리플 빌 10/14 더블8·트윈7 / c 피아노 피아노 10/27 더블8·트윈7.

## 3. 배선 순서 (운영자 실행 1회 = 라이브 경계)

고객이 문자 링크를 누르면 바로 들어와야 한다 — **Cloudflare Access 같은 로그인 벽이 없는 프로젝트**여야 한다.

1. Cloudflare → **Workers & Pages → Create → Pages → Connect to Git** → 이 저장소
2. 빌드 설정
   - Root directory : **비움**(저장소 루트)
   - Build command : **비움**
   - Build output directory : **`public`**
   - Framework preset : None
   - ⚠ `Build output directory` 칸이 안 보이면 그건 Pages가 아니라 Workers다 — 뒤로 가서 Pages로 다시.
3. 생성 후 **Settings → Bindings → R2 bucket**
   - Variable name : **`R2`**
   - Bucket : 아무 버킷 (키가 `booking/` 밑이라 기존 데이터와 안 섞인다)
4. **Settings → Variables and Secrets** → `BOOK_PIN` = 관리자 비번(아무 문자열)
5. 배포 후 나오는 주소가 곧 고객 링크. 관리자는 그 주소 + `/admin.html`
6. 터미널에서 보려면 저장소 루트에 `.booking.json` = `{ "url": "<배포주소>", "pin": "<BOOK_PIN>" }`
   (`.gitignore`에 들어 있어 커밋되지 않는다)

### 배선 확인 3줄 (설치 직후 이 순서로)
1. `/admin.html` 접속 → 비번 입력 → **"저장소(R2)가 연결되지 않았어"** 가 뜨면 3번을 다시(바인딩 이름 확인)
2. **"관리자 비번(BOOK_PIN)이 아직 설정되지 않았어"** 가 뜨면 4번을 다시
3. 명단 한 줄(`1234, a, 테스트`) 저장 → 고객 주소에서 `1234` 입력 → **공연 날짜와 객실 2종**이 보이면 배선 끝

## 4. 건드리기 전에 읽을 계약 4종

### a. 자리 차감 = 파일 1개 + 사후 양보 (`reserve()`)
수량 하나를 파일에 적어두고 빼는 방식이 **아니다.** 그 방식은 두 사람이 같은 순간에 누르면
서로 덮어써서 한 건이 조용히 사라진다(R2에는 잠금이 없다).

대신:
1. **선택 1건 = 자기 번호 이름의 파일 1개** — 키가 유일해서 덮어쓰기 충돌이 구조적으로 불가능
2. 쓴 뒤 **전건을 다시 세어** 자기가 정원 안에 드는지 확인
3. 밀렸으면 자기 파일을 지우고 마감으로 답한다

정렬 기준이 **(시각, 뒷4자리)** 인 게 실효 조건이다 — 두 요청이 같은 판정을 내리므로 한쪽만 살아남는다.
시각만으로 정렬하면 같은 밀리초에 들어온 둘이 서로를 살렸다고 판단해 정원을 넘긴다.
→ **`reserve()`의 정렬 줄과 사후 재확인 블록을 지우지 마라.** 지우면 `test.mjs` [5]가 바로 잡는다.

### b. 재고는 저장하지 않는다
남은 수량은 어디에도 안 적혀 있다. 매번 `cap - 실제 파일 수`로 **계산**한다(`leftOf()`).
그래서 관리자가 수량을 줄여도 기존 선택은 안 지워지고, 취소하면 그 자리가 즉시 다시 열린다.
→ "남은 수량"을 어딘가에 캐시하려는 개선은 하지 마라. 위 a의 안전장치가 통째로 무효가 된다.

### c. 관리자는 변수가 없으면 통째로 잠긴다 (`adminOk()`)
`BOOK_PIN`이 없으면 `nopin`으로 **거절**한다. 기본 비번을 넣거나 빈 문자열을 통과시키면
아무나 명단을 갈아엎을 수 있다. → 기본값 폴백을 넣지 마라.

### d. 날짜는 고객이 고르지 않는다 (260825 추가)
숙박일 선택 UI를 만들지 마라. 고객이 고를 수 있는 날은 하루뿐이고, 그건 명단의 `g`가 정한다.
화면에는 「예매 확정 내역 · 변경 불가」로 **보여주기만** 한다.
그리고 선택이 접수될 때 그 시점의 공연명·숙박일을 **예약 건에 박아 둔다**(`rec.show` · `rec.stayDate` · `rec.stayOut`).
나중에 운영자가 `stock.json`의 날짜를 고쳐도 이미 접수된 사람의 안내 내용은 안 흔들리게 하려는 것이다.
→ 완료 화면·CLI는 예약 건에 박힌 값을 먼저 쓰고, 없을 때만 `stock.json`을 본다. 이 우선순위를 뒤집지 마라.

`admin_stock`은 **보내온 것만 갈아끼운다.** 수량만 저장해도 공연명·날짜는 지금 값을 지킨다(`test.mjs` [9]).
날짜 형식(`YYYY-MM-DD`)이 아니면 무시하고 이전 값을 남긴다.

## 6. 아직 안 된 것 · 다음 후보

- **a. 뒷 4자리 중첩** — 지금은 명단 저장 시 **뒤엣것을 버리고** 어느 번호가 겹쳤는지 알린다(`parseRoster()`의 `dups`).
  운영자가 "겹치는 사람 생겼다"고 하면 → 인증 화면에서 **이름 한 글자**나 **생년 4자리**를 같이 묻는 2차 확인으로 넓힌다.
  손댈 자리 = `roster.json` 값 구조(`{g,n}` → 배열) + `auth` 분기 + `index.html` 1단계. **지금 구조로는 못 한다.**
- **b. 관리자 화면 = 카드 목록** — 260825에 표를 카드로 바꿨다(폰 390에서 취소 버튼이 밀려나던 자리).
  표로 되돌리지 마라. 열을 늘려야 하면 카드 안에 줄을 더한다.
- **c. 실제 R2 위에서의 동작 미확인** — 검증은 R2를 흉내 낸 판에서 돌렸다.
  `list`의 일관성·페이지 넘김은 실배포에서 한 번 봐야 한다(§3 배선 확인 3줄이 그 최소 확인이다).
- **d. 문자 발송** — 이 프로그램 밖이다. 링크만 넘긴다.
- **e. 취소 이력** — 관리자가 취소하면 파일이 지워지고 기록이 안 남는다. 필요하면 `booking/log/` 축을 신설.
- **f. 디럭스 상향** — 홍보물에 「숙박 시설 사정에 따라 디럭스로 상향될 수 있다(예매 순서 기준)」가 있다.
  지금은 고객 화면에 **문구로만** 있다. 실제로 상향 대상을 시스템이 고르게 하려면 `bk/*.json`에 등급 칸을 신설한다.
- **g. 마감 시각** — 「각 공연 시작일 6일 전 17:00」 이후엔 선택을 막아야 할 수 있다.
  지금은 시간 제한이 없다. 넣는다면 `shows[g].date`에서 역산해 `auth`·`book` 양쪽에서 막아야 한다(한쪽만 막으면 뚫린다).
